# Design

## Context

См. `proposal.md` — Why. Состояние, влияющее на подход:

- `DepartmentController.changeById` (`DepartmentController.java:147`) принимает
  `DepartmentRequestDto` без `@Valid`; DTO — record `{ name, type, parentId }` без
  аннотаций.
- `DepartmentDtoService.changeById` (`DepartmentDtoService.java:62`) проверяет
  дубликат через `existDepartment(name)`, который учитывает и сам обновляемый
  департамент; родителя назначает только при `parentId != null`; архивного
  родителя молча игнорирует.
- `DepartmentService.findById` (`DepartmentService.java:47`) бросает
  `IllegalArgumentException`; `GlobalExceptionHandler` превращает его в `400`.
- В БД уже есть регистронезависимый уникальный индекс
  (`ux_department_name_lower_icu`), а `GlobalExceptionHandler` уже распознаёт его
  и `uc_department_name` и отдаёт `400` с сообщением о дубликате.
- `DepartmentRepository.existsByNameCaseInsensitive` — native-запрос с
  `COLLATE "ru-RU-x-icu"`; производный Spring Data метод без collation был бы
  регистрозависимым и разошёлся бы с индексом.
- `DepartmentService.findById` используется также в `EmployeeService.save`
  (`EmployeeService.java:39`) и при создании департамента с родителем.

## Goals / Non-Goals

**Goals:**

- Сделать `PUT` предсказуемым: валидация, дубликаты, циклы, архивы, `404`,
  точные сообщения и единый формат ошибок.
- Опираться на ограничение БД как на единственный источник истины для
  уникальности имени.
- Разрешить явную очистку родителя.
- Не менять модель данных и не добавлять миграции.

**Non-Goals:**

- Новые endpoint'ы и изменение ответов других методов, кроме неизбежного
  `400` → `404` для отсутствующего департамента.
- Блокировки строк и защита от гонок на уровне БД сверх существующих ограничений.
- Изменение UI и правил отображения корневого уровня каталога.
- История версий и откат изменений департамента.

## Decisions

### 1. Валидация на общем DTO

`DepartmentRequestDto` получает `@NotBlank(message = "Название департамента обязательно")`,
`@Size(max = 255, message = "Название не должно превышать 255 символов")` и
`@NotNull(message = "Некорректный тип департамента")` для `type`. Контроллеры
`create` и `changeById` получают `@Valid`.

Почему общий DTO: форма запроса у создания и обновления одинаковая, а UI уже
требует имя и тип при создании. Тексты задаются явно, иначе в `message` попадёт
английское сообщение по умолчанию.

Альтернатива — отдельный `DepartmentUpdateRequestDto`. Отвергнута: дублирование
полей и риск расхождения контрактов без выигрыша.

### 2. Обработчики ошибок валидации

`GlobalExceptionHandler` добавляет:

- `MethodArgumentNotValidException` → `400`, сообщение первого нарушения из
  `FieldError.getDefaultMessage()`.
- `HttpMessageNotReadableException` → `400`: если причина —
  `InvalidFormatException` с путём `type`, сообщение
  `Некорректный тип департамента`; иначе `Некорректное тело запроса`.

Почему: недопустимый enum падает в Jackson раньше bean validation. Без
обработчика Spring отдаёт свой формат без поля `message`, и UI показывает общий
текст вместо точной причины.

### 3. Дубликат имени — только ограничение БД

Предварительная проверка `existDepartment(dto.name())` удаляется из
`changeById`. Уникальность обеспечивает функциональный уникальный индекс
`ux_department_name_lower_icu`; обновление строки тем же именем (включая смену
регистра) индекс не нарушает.

Чтобы нарушение всплывало до завершения транзакции и попадало в существующий
обработчик `DataIntegrityViolationException` → `400`, сохранение выполняется с
явным flush (`saveAndFlush`) внутри `changeById`. Без этого UPDATE может
уйти в commit после возврата из сервиса, и тип исключения будет зависеть от
транзакционной инфраструктуры.

Альтернативы:

- `existsByNameCaseInsensitiveAndIdNot` — требует native-запроса с тем же
  `COLLATE`, дублирует знание об индексе и оставляет окно гонки.
- Оставить предварительную проверку — ловит сам обновляемый департамент и
  запрещает сохранение без изменения имени.

Создание (`save`) не меняется: там предварительная проверка остаётся.

### 4. `404` для отсутствующих сущностей

Новое `DepartmentNotFoundException`; `DepartmentService.findById` бросает его
вместо `IllegalArgumentException`, обработчик отдаёт `404` с существующим
форматом.

Следствия: создание с несуществующим родителем и `EmployeeService.save`
начнут отдавать `404` вместо `400`. Это соответствует контракту; существующие
тесты и документация обновляются.

Альтернатива — оставить `IllegalArgumentException` и маппить по тексту.
Отвергнута: хрупко и смешивает `400`/`404`.

### 5. Циклы

- `parentId == id` → `400` с сообщением о самородителе.
- Для кандидата в родители выполняется подъём по цепочке `parent`; если
  встречается обновляемый департамент → `409` с сообщением о дочернем
  подразделении.
- Обход защищён множеством посещённых `id`, чтобы уже испорченные данные с циклом
  не зациклили проверку.
- Дерево небольшое, поэтому обход в памяти проще и тестируемее CTE.

### 6. Архив и очистка родителя

- Архивный обновляемый департамент → `409` (`Департамент удалён и не может быть изменён`).
- Архивный родитель проверяется явно и даёт `409` (`Родительский департамент удалён`),
  а не игнорируется.
- `department.setParent(parent)` выполняется всегда, включая `parent == null`.

### 7. Нарушения целостности

`DataIntegrityViolationException` остаётся `400`. Дубликат распознаётся по имени
ограничения и получает сообщение о существующем названии; остальные нарушения —
`Не удалось сохранить департамент`.

## Risks / Trade-offs

- **Ошибка уникальности всплывает на commit, а не на flush** → сохранять через
  `saveAndFlush`, чтобы исключение гарантированно прошло через трансляцию
  Spring Data и обработчик.
- **Общий DTO меняет и создание** → `@Valid` на `create` может отклонить тела,
  которые раньше падали на NOT NULL или молча сохранялись. Это согласуется с
  правилами UI; тесты создания обновляются.
- **`findById` → `404` затрагивает сотрудников и создание** → обновить тесты и
  документацию; изменение соответствует контракту.
- **Гонка между проверкой цикла и сохранением** → транзакция и ограничения БД;
  полноценная блокировка строк не вводится.
- **Повреждённые данные с существующим циклом** → обход с множеством посещённых
  узлов не зависает.
- **`@Size` считает пробелы до trim** → имя из 256 символов с пробелами по краям
  может быть отклонено, хотя после trim короче. UI обрезает пробелы до отправки;
  риск признан несущественным.
- **`findById` не фильтрует архивных** → архивность проверяется отдельно и явно.

## Migration Plan

1. Выпустить бэкенд: DTO-валидация, обработчики, исключения, проверки, flush,
   тесты.
2. Проверить `curl`-сценарии: успех, дубликат, неизменное имя, самородитель,
   потомок, архивный родитель, отсутствующий `id`, очистка родителя.
3. После этого внедрять UI-часть `add-department-edit`; без явной очистки
   родителя сценарий «очистить родителя» в UI не даст эффекта.
4. Архивация change после ревью; дельта `department-api` сливается с durable-спекой.

Откат: вернуть прежнюю проверку дубликата и `IllegalArgumentException`; модель
данных и миграции не затрагиваются. UI-часть можно откатить независимо.
