# Design

## Context

См. `proposal.md` — Why. Состояние, влияющее на подход:

- `DepartmentDtoService.save` валидирует DTO, проверяет дубликат и при
  `parentId != null` ищет родителя, но не требует родителя для не-`FACTORY`.
- `DepartmentDtoService.changeById` уже проверяет архив, самородителя,
  существование/архив/цикл родителя и очищает `parent` при `parentId == null`;
  ограничения «родитель обязателен для не-`FACTORY`» нет.
- `DepartmentType` содержит `FACTORY`, `WORKSHOP`, `AREA`, `LABORATORY`.
- `@Valid` на DTO уже проверяет `name` и `type`; `parentId` остаётся
  необязательным на уровне аннотаций.
- UI-создание уже требует родителя для не-`FACTORY`, но API это не гарантирует;
  UI-редактирование в `add-department-edit` будет опираться на новое правило.

## Goals / Non-Goals

**Goals:**

- Запретить создание и обновление не-`FACTORY` без родителя.
- Оставить `FACTORY` возможность быть без родителя, иметь родителя и очищать его.
- Сохранить существующий формат ошибок `{ message, status, timestamp }` и код `400`.
- Выявить уже существующие записи без родителя, не выполняя автоматическую миграцию.

**Non-Goals:**

- Изменение корневого списка каталога и показ orphan-узлов.
- Автоматическое перепривязывание или удаление существующих записей.
- Новые endpoint'ы, миграции схемы БД, изменение типа департамента через UI.
- Изменение правила дубликата имени и других проверок PUT.

## Decisions

### 1. Проверка в сервисном слое

Правило проверяется в `DepartmentDtoService` до сохранения:

```text
if (dto.type() != FACTORY && dto.parentId() == null) {
    throw new IllegalArgumentException("Родительский департамент обязателен");
}
```

Почему сервис, а не аннотация: правило зависит от двух полей (`type` и
`parentId`), а `DepartmentRequestDto` — record без класса; условная валидация
потребовала бы отдельного валидатора и усложнила порядок ошибок.

Порядок проверок:

- создание: наличие родителя для не-`FACTORY` → дубликат имени → поиск родителя;
- обновление: поиск департамента → архив → наличие родителя для не-`FACTORY` →
  самородитель/цикл/архив родителя.

`IllegalArgumentException` уже обрабатывается `GlobalExceptionHandler` как `400`,
поэтому новый класс исключения не нужен.

### 2. Поведение FACTORY

`FACTORY` может быть без родителя, иметь родителя и очищать его. Это не создаёт
orphan: корневой список выбирает `FACTORY` по типу, а `FACTORY` с родителем
остаётся видимым и в корне, и в ветке родителя. Поэтому проверка наличия
родителя применяется только к `WORKSHOP`, `AREA`, `LABORATORY`.

### 3. Использовать тип из запроса

Правило опирается на `dto.type()`, а не на текущий тип сущности: тип можно
изменить через API, и запрос должен быть согласован сам с собой. UI тип не
меняет и всегда присылает текущий. Если клиент меняет `FACTORY` на `WORKSHOP`
без родителя, он получает `400`.

### 4. Аудит существующих данных

Новое правило не исправляет уже созданные записи `type <> 'FACTORY' AND
parent_id IS NULL`. Добавляется задача аудита: найти такие строки и вручную
решить, перепривязать их или архивировать. Автоматическая миграция не входит в
change, потому что требует продуктного решения по каждой записи.

## Risks / Trade-offs

- **Ломается API-клиент, создававший не-`FACTORY` без родителя** → это намеренное
  изменение по политике D; UI уже требует родителя, ошибка возвращается как
  `400` с понятным сообщением.
- **Существующие orphan-записи остаются** → аудит и ручное решение; правило
  предотвращает только новые записи.
- **Тип в запросе может отличаться от текущего** → правило использует `dto.type()`,
  что соответствует сохраняемому состоянию; UI всегда присылает текущий тип.
- **Порядок ошибок может измениться** → при одновременном дубликате и отсутствии
  родителя сначала возвращается ошибка родителя; это задокументировано в дизайне
  и не влияет на UI, который валидирует форму заранее.
- **UI-редактирование зависит от нового правила** → выкатить бэкенд до UI; иначе
  UI сможет отправить очистку родителя и получит неожиданный успех.

## Migration Plan

1. Выпустить бэкенд с проверкой родителя; обновить README с порядком выпуска.
2. Выполнить аудит существующих записей без родителя; решение по ним — вручную.
3. После этого внедрять UI-часть `add-department-edit` с запретом очистки для
   не-`FACTORY`.
4. Архивировать change после ревью; обновить durable-спеку `department-api`.

Откат: убрать проверку родителя из `save` и `changeById`; схема БД и данные не
затрагиваются. UI-часть можно откатить независимо.
