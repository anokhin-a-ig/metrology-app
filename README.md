# metrology-app

## Правило родительского департамента

- `FACTORY` может быть без родителя, может иметь родителя и может очищать его
  (`parentId: null`).
- `WORKSHOP`, `AREA` и `LABORATORY` обязаны иметь родителя при создании и
  обновлении. Без `parentId` бэкенд возвращает `400` с сообщением
  `Родительский департамент обязателен`.
- Очистка родителя у не-`FACTORY` запрещена: `parentId: null` для таких типов
  отклоняется тем же `400`.

## Порядок выпуска изменений контракта департаментов

Изменения контракта `POST /api/v1/departments` и `PUT /api/v1/departments/{id}`
(обязательный родитель для не-`FACTORY`, валидация тела, коды `400`/`404`/`409`,
очистка родителя) выкатываются в бэкенд **до** внедрения UI-части
`add-department-edit` в `metrology-app-ui`.

Порядок выпуска:

1. Выпустить бэкенд `metrology-app` с правилом обязательного родителя и
   обновлённым контрактом обновления департамента.
2. Проверить `POST`/`PUT` (Swagger или `curl`): создание не-`FACTORY` без
   родителя → `400`, с родителем → `201`; создание `FACTORY` → `201`;
   обновление не-`FACTORY` без родителя → `400`; `FACTORY` без родителя → `200`.
3. После этого внедрять и выпускать UI-часть `add-department-edit` с запретом
   очистки родителя для не-`FACTORY`.

Откат: убрать проверку обязательного родителя из `save` и `changeById`; UI-часть
можно откатить независимо. Схема БД и данные не затрагиваются.

### Очистка родителя

Очистить родителя можно только у `FACTORY`: UI передаёт `parentId: null` (или не
передаёт поле), бэкенд выполняет `department.setParent(null)` и возвращает `200`
с `parent: null`. Для не-`FACTORY` такой запрос возвращает `400`.

### Аудит существующих записей

Правило не исправляет уже созданные записи
`type <> 'FACTORY' AND parent_id IS NULL`. Их нужно найти запросом и вручную
перепривязать к родителю или архивировать; автоматическая миграция не
выполняется.
